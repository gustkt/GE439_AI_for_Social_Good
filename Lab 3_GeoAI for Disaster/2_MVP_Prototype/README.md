# GeoAI-for-Disaster — ระบบแจ้งเตือนฟ้าผ่าล่วงหน้าสำหรับสนามไทยลีก 1

> ⚠ **ต้นแบบเชิงวิชาการ — ไม่ใช่ระบบเตือนภัยสำหรับตัดสินใจจริง**
> ตำแหน่งฟ้าผ่าและฝนมีความคลาดเคลื่อนตามข้อจำกัดของเครือข่ายตรวจจับที่ใช้
> Radar data © [RainViewer](https://www.rainviewer.com)

MVP สำหรับวิชา lab หัวข้อ GeoAI-for-Disaster ระบบรวมข้อมูลจริง 2 ทาง คือ **ฟ้าผ่า** และ
**เรดาร์ฝน** รอบสนามฟุตบอลไทยลีก 1 ฤดูกาล 2026-27 จัดระดับความเสี่ยงตามเกณฑ์ NCAA
**พยากรณ์ล่วงหน้า** ว่าพายุจะมาถึงสนามเมื่อไร และแสดงผลบนแผนที่

ระบบครบทั้งเส้น **Data → Model → API → UI** และ **ใช้ข้อมูลจริงเท่านั้น ไม่มีโหมดข้อมูลจำลอง**

## เริ่มใช้งาน

### วิธีที่ง่ายที่สุด (Windows): ดับเบิลคลิก `start.bat`

1. ต้องมี **Python 3.10 ขึ้นไป** (ถ้ายังไม่มี ติดตั้งจาก <https://www.python.org/downloads/> และติ๊ก *Add python.exe to PATH*)
2. แตกไฟล์ zip แล้ว **ดับเบิลคลิก `start.bat`**
3. ครั้งแรกจะสร้าง `.venv` และติดตั้งแพ็กเกจ (ต้องต่ออินเทอร์เน็ต ราว 1–2 นาที) จากนั้นเบราว์เซอร์จะเปิดหน้าเว็บให้เอง
4. ปิดหน้าต่างดำเพื่อหยุดเซิร์ฟเวอร์ ครั้งต่อไปดับเบิลคลิกได้เลย เปิดเร็วกว่าครั้งแรก

ไม่ต้องมี API key: ระบบใช้ฟ้าผ่าสดจาก Blitzortung (ฟรี) และเรดาร์จาก RainViewer
ถ้าพอร์ต 8000 ถูกใช้อยู่ จะเปิดที่ <http://127.0.0.1:8765> แทน

**ลองดูอะไรบ้าง**
- **โหมดสด:** รอเรดาร์โหลด 1–2 นาที สนามจะเปลี่ยนจาก "ไม่มีข้อมูล" เป็นเฝ้าระวัง/ปลอดภัยตามฝนจริงขณะนั้น
- **Replay พายุจริง:** กดปุ่ม "Replay พายุจริง" → "ช่วงใกล้สุด" จะเห็นสนาม PT Prachuap (Sam Ao) ขึ้นอันตราย
  หรือเปิดตรง ๆ: <http://127.0.0.1:8000/?mode=replay&file=capture_20260916T054352Z_storm.jsonl&t=2026-09-16T06:52:00Z&stadium=11&zoom=10>

### วิธีรันด้วยคำสั่งเอง (ทุกระบบปฏิบัติการ)

```bash
python -m venv .venv
.venv\Scripts\activate          # macOS / Linux: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env          # macOS / Linux: cp .env.example .env
uvicorn app.main:app --reload
```

เปิด <http://127.0.0.1:8000>

ตอน startup ระบบสร้างฐานข้อมูล SQLite, seed สนามจาก `data/thai_league1_2026-27_stadiums.geojson`
และเริ่มดึงภาพเรดาร์ย้อนหลัง 2 ชม. ทันที (ใช้เวลาราว 1–2 นาทีในรอบแรก)

ตรวจสถานะได้ที่ <http://127.0.0.1:8000/api/health> ดู `lightning_available` และ `radar_available`

บนแผนที่โหมดสด: ไอคอนสายฟ้าจาง ๆ ทั่วประเทศ = ฟ้าผ่าจริงชั่วโมงล่าสุด (`/api/strikes/region`)
ไอคอนสายฟ้าชัดรอบสนามที่เลือก = ฟ้าผ่า 30 นาทีที่ใช้ตัดสินสถานะ

## สถาปัตยกรรม: รวมหลักฐาน 2 ทาง (fusion)

| ข้อมูล | บทบาท | ทำให้ขึ้นสถานะ |
|--------|--------|---------------|
| **ฟ้าผ่า** (Xweather / Blitzortung / replay) | หลักฐานสั่งหยุด | `WATCH`, `SUSPEND`, `DANGER` |
| **เรดาร์ฝน** (RainViewer) | สัญญาณเตือนล่วงหน้า | `WATCH` เท่านั้น |

ทำไมเรดาร์สั่งหยุดแข่งไม่ได้: ฝนหนักไม่เท่ากับฟ้าผ่า ช่วงหน้าฝนมี cell ≥ 40 dBZ บ่อยทั้งที่ไม่มีฟ้าผ่า
ถ้าให้เรดาร์สั่งหยุด สนามจะถูกระงับบ่อยจนไม่มีใครเชื่อระบบ และเกณฑ์ NCAA นิยามจากระยะฟ้าผ่า
ไม่ใช่ฝน ส่วนเรดาร์มีค่าตรงที่ **ลดจุดบอด** ของเครือข่ายตรวจฟ้าผ่า เห็นพายุก่อนมันเริ่มปล่อยประจุ
หรือตอนที่ข้อมูลฟ้าผ่าพลาด

**"ไม่มีข้อมูล" ไม่ใช่ "ปลอดภัย"** — ถ้าข้อมูลฟ้าผ่าไม่พร้อม (quota หมด, หลุดการเชื่อมต่อ,
ข้อมูลขาดช่วงเกิน 3 นาที, stream ค้างเกิน 2 นาที) และไม่มีหลักฐานอื่น สถานะจะเป็น `NO_DATA` ไม่ใช่ `ALL_CLEAR`

**เครือข่ายที่จับได้ไม่ครบต้องมีเรดาร์ยืนยัน** — ถ้าข้อมูลฟ้าผ่าที่ใช้ได้ตอนนี้มาจาก Blitzortung อย่างเดียว
(สถานีในไทยน้อย ฟ้าผ่าอ่อนอาจหลุด) การไม่เห็นฟ้าผ่ายังไม่พอ จะขึ้น `ALL_CLEAR` ได้เมื่อเรดาร์พร้อม
และไม่พบฝนแรงในวง 16 กม. ถ้าเรดาร์ไม่พร้อมจะเป็น `NO_DATA`
แต่ strike ที่บันทึกไว้แล้วยังนับตามปกติ เช่น quota หมดกลางพายุ สนามที่ SUSPEND อยู่จะไม่หายไป

## เกณฑ์ความปลอดภัย

| สถานะ | เงื่อนไข | ความหมาย |
|-------|---------|-----------|
| `DANGER` | strike ≤ 10 กม. ใน 30 นาที | ทุกคนต้องอยู่ในที่กำบังแล้ว |
| `SUSPEND` | strike ≤ 13 กม. ใน 30 นาที | เกณฑ์ NCAA — ระงับแข่ง เริ่มอพยพ |
| `WATCH` | strike ≤ 16 กม. **หรือ** เรดาร์พบฝน ≥ 40 dBZ ในรัศมี 16 กม. | แจ้ง safety officer เตรียมพร้อม |
| `NO_DATA` | ข้อมูลฟ้าผ่าไม่พร้อม และไม่มีหลักฐานข้างบน | ยังยืนยันไม่ได้ว่าปลอดภัย |
| `ALL_CLEAR` | ไม่มี strike ≤ 13 กม. 30 นาที **และ** ไม่มีฝนแรงในรัศมี 16 กม. **และ** ข้อมูลฟ้าผ่าพร้อม | แข่งต่อได้ |

13 กม. ≈ 8 ไมล์ คือเกณฑ์ระงับการแข่งขันของ NCAA Lightning Safety เพราะฟ้าผ่ากระโดดออกจาก
เมฆฝนได้ไกลระดับ 10 กม. ส่วน all-clear 30 นาทีเป็นมาตรฐาน และ strike ใหม่ในวง 13 กม.
รีเซ็ตนาฬิกาใหม่ทั้งหมด (strike ที่ 15 กม. ขึ้น WATCH ได้แต่ไม่รีเซ็ตนาฬิกา)

ถ้าเรดาร์ไม่พร้อมและมี Xweather ใช้ได้ ระบบยังตอบ `ALL_CLEAR` ได้ แต่จะแนบเหตุผลว่า "ไม่มีข้อมูลเรดาร์ประกอบ"
ถ้ามีแต่ Blitzortung จะเป็น `NO_DATA` (ดูหัวข้อ fusion)

## GeoAI ในระบบนี้

### 1. ตรวจ hotspot และ cell ฝนแรงจากภาพเรดาร์ — `app/model/radar_cells.py`

1. แปลงสีแต่ละ pixel เป็นค่า **dBZ** ด้วยตารางสีทางการของ RainViewer (`data/rainviewer_colors.csv`)
   โดยขอภาพแบบปิด smoothing เพื่อให้สีตรงตาราง 100%
2. **hotspot** = pixel ที่ dBZ ≥ 40 (ตัวแทนฝนฟ้าคะนองแบบ convective ที่ใช้กันทั่วไป)
3. จัดกลุ่ม hotspot ที่ติดกัน (8 ทิศ) เป็น **cell** ตัด cell ที่เล็กกว่า 4 pixel (~6 ตร.กม.) เป็นสัญญาณรบกวน
4. ต่อสนาม: ระยะถึง hotspot ที่ใกล้ที่สุด, dBZ สูงสุดในวง 16 กม. และจุดศูนย์ถ่วงของฝนแรงในรัศมี 50 กม.

### 2. Nowcast — `app/model/nowcast.py`

ใช้สูตรเดียวกันกับข้อมูล 2 ชนิด:

| | ฟ้าผ่า | เรดาร์ |
|--|-------|-------|
| จุดที่ติดตาม | strike แต่ละครั้ง | จุดศูนย์ถ่วงของฝนแรงรอบสนามในแต่ละภาพ |
| หน้าต่าง / ถังเวลา | 20 นาที / 5 นาที | 40 นาที / 10 นาที (ภาพออกทุก 10 นาที) |
| ETA ถึงวง | 13 กม. (สั่งหยุด) | 16 กม. (เฝ้าระวัง) |

ขั้นตอน: แบ่งถังตาม **เวลาที่เกิดจริง** → หา centroid แต่ละถัง → fit เวกเตอร์การเคลื่อนที่ด้วย
**least squares** → แก้สมการกำลังสองหาเวลาที่แตะวง ผลเป็น `null` เมื่อข้อมูลไม่พอหรือทิศไม่ชัด
พร้อมเหตุผลเสมอ

**ข้อจำกัด:** สมมติการเคลื่อนที่เป็นเส้นตรงความเร็วคงที่ ไม่จำลองการก่อตัว/สลายตัวของ cell
ภาพเรดาร์เป็นค่าสะท้อนรวมทุกความสูง บอกได้ว่ามีฝนแรง แต่บอกไม่ได้ว่ามีประจุไฟฟ้า

## แหล่งข้อมูล

### ฟ้าผ่า — เลือกด้วย `LIGHTNING_SOURCE` (ใช้หลายแหล่งพร้อมกันได้ คั่นด้วยจุลภาค)

| ค่า | ลักษณะ | badge บนหน้าเว็บ |
|-----|--------|-----------------|
| `blitzortung,xweather` | **ค่าแนะนำ** รันทั้งสองพร้อมกัน ตัดฟ้าผ่าซ้ำ (≤ 1 วินาที, ≤ 5 กม.) | `BLITZORTUNG (LIVE · ฟรี) + XWEATHER (...)` |
| `blitzortung` | stream ฟรี ไม่มี quota แต่จับได้ไม่ครบในไทย | `BLITZORTUNG (LIVE · ฟรี)` สีเขียว |
| `xweather` | polling ทุก 60 วิ มี quota ครบกว่า | `XWEATHER (LIVE · ...)` สีเขียว |
| `replay` | เล่นข้อมูลจริงที่ capture ไว้ (ใช้เดี่ยว ๆ) | `REPLAY ข้อมูลจริง <วันที่>` สีฟ้า |

ไม่มี key ของ Xweather ก็ใช้ `blitzortung,xweather` ได้ ระบบจะข้าม Xweather แล้วใช้ Blitzortung อย่างเดียว
(ดูว่าแหล่งไหนทำงานอยู่ได้ที่ `/api/meta` → `source_status.sources`)

#### Xweather

```ini
LIGHTNING_SOURCE=xweather
XWEATHER_CLIENT_ID=<client id>
XWEATHER_CLIENT_SECRET=<client secret>
XWEATHER_STADIUM_IDS=all
```

- ต้องใช้ **คู่** `client_id` + `client_secret` — API key เดี่ยวได้ HTTP 401
- free tier: lightning มี multiplier ×10, **ย้อนหลังได้แค่ 5 นาที**, รัศมีสูงสุด 100 กม.
- `XWEATHER_STADIUM_IDS`: `all` = ทุกสนามทุก 60 วิ (840 call/ชม.), `2,3` = เฉพาะสนามที่เลือก
  (สนามอื่นแสดงสีเทา "ไม่ได้เฝ้าระวัง"), ว่าง = วนทีละกลุ่ม (แต่ละสนามถูกเช็กทุก ~14 นาที)
- **quota หมด:** API ตอบ HTTP 429 + `maxhits` ระบบจะหยุดยิงทันที แจ้ง `NO_DATA` ทุกสนาม
  และลองใหม่ทุก `XWEATHER_RETRY_MINUTES` (60) นาที เมื่อ quota รอบใหม่เริ่มจะกลับมาใช้ได้เอง
- `client_secret` อยู่ใน URL ของ request ระบบจึงปิด log ระดับ INFO ของ httpx ไว้

#### Blitzortung

ต่อ WebSocket ที่หน้าแผนที่ของเขาใช้ (`wss://wsN.blitzortung.org/` ส่ง `{"a":111}` แล้วรับ frame
บีบอัด LZW) wire protocol ศึกษาจาก
[kevinkiyosepyo/Lightning-Data-Pipeline-API](https://github.com/kevinkiyosepyo/Lightning-Data-Pipeline-API)
แล้วเขียนใหม่เองใน `app/sources/blitzortung.py`

> **ข้อค้นพบ:** 2026-09-15 ขณะมีพายุจริงห่าง True BG 17–25 กม. (ยืนยันด้วย Xweather)
> Blitzortung ส่ง strike มา 2,198 จุดใน 5 นาทีครึ่ง แต่ตกในไทย 0 จุด / 2026-09-17 ตรวจซ้ำพบว่า feed
> มีข้อมูลเอเชียจริง และภาพแผนที่ Asia ของ Blitzortung (`docs/figures/blitzortung_asia_snapshot.png`,
> CC BY-SA 4.0) เห็นฟ้าผ่าในไทย/กัมพูชา/ลาว แต่ความถี่ต่ำ สรุป: **ครอบคลุมไทยแต่จับได้ไม่ครบ**
> ระบบจึงใช้เป็นแหล่งฟรีที่ส่งข้อมูลสดตลอด คู่กับกฎ "ต้องมีเรดาร์ยืนยันก่อน ALL_CLEAR"
> และตรวจว่า stream ค้างหรือไม่ (ไม่มี frame เกิน `BLITZORTUNG_STALE_SECONDS` = 120 วินาที = ไม่พร้อม)

เงื่อนไขการใช้ข้อมูลของ Blitzortung: ใช้ได้เฉพาะงานไม่เชิงพาณิชย์ ห้ามใช้เพื่อความปลอดภัย
และ raw data เป็นของเจ้าของสถานี การอ่าน feed ของหน้าแผนที่จึงเป็นพื้นที่สีเทา

## Capture / Replay — demo ด้วยข้อมูลจริงแม้วันนำเสนอฟ้าใส

**1. Capture** — เปิด `CAPTURE=true` แล้วรันทิ้งไว้ช่วงมีพายุ
ระบบบันทึกลง `data/captures/capture_<เวลา UTC>.jsonl` ทั้ง **strike ที่อยู่ใกล้สนาม** และ
**ผลวิเคราะห์ภาพเรดาร์ทุกภาพ** (cell + ระยะถึงสนาม ไม่ใช่ภาพดิบ) กรองตัวซ้ำให้แล้ว

**2. Replay** — เล่นย้อนหลังตอนนำเสนอ

```ini
LIGHTNING_SOURCE=replay
REPLAY_FILE=capture_20260916T054352Z_storm.jsonl
REPLAY_SPEED=1
```

ทุก record ถูกเลื่อนเวลาด้วยค่าคงที่เดียวกัน ความสัมพันธ์ทางเวลาระหว่างฟ้าผ่ากับเรดาร์จึงเหมือนตอน
ที่เกิดจริง ระหว่าง replay ระบบไม่ดึงเรดาร์สด เพื่อไม่ให้ข้อมูลต่างเวลาปนกัน

- ไฟล์ที่ capture ก่อน 2026-09-17 (เช่น พายุ 16 ก.ย.) มีแต่ฟ้าผ่า หน้าเว็บจะแจ้งว่าไม่มีข้อมูลเรดาร์
- `REPLAY_SPEED` มากกว่า 1 ทำให้ demo สั้นลง แต่ความเร็วพายุและนาฬิกา all-clear จะไม่ตรงความจริง

### Replay บนหน้าเว็บ (แนะนำสำหรับนำเสนอ)

กดปุ่ม **Replay พายุจริง** ในแผง "โหมดแสดงผล" ได้ทันที ไม่ต้องแก้ `.env` หรือรีสตาร์ท
ระหว่างนั้นเซิร์ฟเวอร์ยังเก็บข้อมูลสดต่อไปตามปกติ

- เลือกเหตุการณ์ → ระบบซูมไปสนามที่พายุเข้าใกล้ที่สุดให้เอง
- ลากแถบเวลา, กด ▶ เล่น (1x / 10x / 30x / 60x) หรือกด "ช่วงใกล้สุด" เพื่อข้ามไปช่วงสำคัญ
- badge และแถบสถานะบอกวันเวลาของข้อมูลจริงตลอด

**ต่างจาก `LIGHTNING_SOURCE=replay` ตรงไหน:** backend คำนวณสถานะ "ณ เวลาเสมือน" ที่เลือก
จากไฟล์ capture โดยตรงด้วยสูตรชุดเดียวกับโหมดสด (`app/replay_view.py` → `app/risk.py`)
ความเร็วพายุและนาฬิกา all-clear จึงตรงความจริงทุกความเร็วที่เล่น ไม่เพี้ยนแบบ `REPLAY_SPEED`

**ข้อสมมติ:** ไฟล์ capture บันทึกเฉพาะสิ่งที่พบ ไม่ได้บันทึกช่วงที่แหล่งข้อมูลล่ม ระบบจึงถือว่า
ข้อมูลฟ้าผ่าพร้อมตลอดช่วงที่บันทึก (พายุ 16 ก.ย. มีช่วงรีสตาร์ทเซิร์ฟเวอร์ราว 2 นาทีที่ไม่ได้บันทึก)

พายุ 16 ก.ย. ถูกรวมจาก 2 ไฟล์ (รีสตาร์ทกลางพายุ) เป็น `capture_20260916T054352Z_storm.jsonl`
ไฟล์ต้นฉบับเก็บไว้ที่ `data/captures/raw/`

### ระบบนี้ไม่มีโหมดข้อมูลจำลอง

ทุกตัวเลขที่แสดงมาจากข้อมูลจริง ไม่ว่าจะรับสดหรือเล่นซ้ำจากที่บันทึกไว้ ข้อมูลสังเคราะห์มีเฉพาะใน
`tests/` (`storm_fixture.py` และ tile ในเทสต์เรดาร์) เพื่อตรวจว่าสูตรคำนวณถูกต้อง ไม่เชื่อมกับระบบที่รันจริง

## API

| Endpoint | ใช้ทำอะไร |
|----------|-----------|
| `GET /api/stadiums` | รายชื่อสนาม (`?active_only=true`) |
| `GET /api/risk?stadium_id={id}` | สถานะรวม, เหตุผล (`status_reasons`), ข้อมูลฟ้าผ่า, ข้อมูลเรดาร์, ETA ทั้ง 2 ทาง, นับถอยหลัง all-clear |
| `GET /api/risk` | สรุปทุกสนาม active เรียงจากเสี่ยงมากไปน้อย |
| `GET /api/strikes/recent?stadium_id={id}&minutes=30` | strike สำหรับวาดบนแผนที่ |
| `GET /api/radar` | ภาพเรดาร์ล่าสุด: cell ฝนแรง + URL tile สำหรับแผนที่ |
| `GET /api/replays` | รายการพายุจริงที่บันทึกไว้ พร้อมสนามที่ได้รับผลกระทบ |
| `GET /api/replays/{file}/risk?t=` | สถานะทุกสนาม ณ เวลาเสมือน t |
| `GET /api/replays/{file}/strikes?stadium_id=&t=` | strike รอบสนาม ณ เวลาเสมือน t |
| `GET /api/replays/{file}/radar?t=` | cell ฝนแรง ณ เวลาเสมือน t |
| `GET /api/meta` | แหล่งข้อมูล, ความพร้อมของฟ้าผ่าและเรดาร์, เครดิต, disclaimer |
| `GET /api/health` | สุขภาพระบบ ตัวนับคำขอ และข้อมูลที่เก็บ |

เอกสาร OpenAPI: <http://127.0.0.1:8000/docs>

## โครงสร้างโปรเจกต์

```
app/
  main.py            FastAPI + static + เปิดตัวรับฟ้าผ่าและเรดาร์ตอน startup
  config.py          อ่าน .env ที่เดียว
  ingest.py          รับข้อมูลกลาง: กรองระยะ + เขียน DB + capture (ฟ้าผ่าและเรดาร์)
  risk.py            ประกอบผลความเสี่ยงของสนาม (ใช้ร่วมกันทั้งโหมดสดและ replay)
  replay_view.py     API ของโหมด replay บนหน้าเว็บ (คำนวณ ณ เวลาเสมือน)
  db.py              schema, helper, cleanup ของ SQLite
  seed_db.py         โหลดสนามจาก GeoJSON
  geo.py / timeutil.py
  sources/
    base.py          LightningSource (async run, availability) + Strike
    xweather.py      polling + จัด cluster + จัดการ quota หมด
    blitzortung.py   stream + LZW decoder + ตรวจ stream ค้าง
    merged.py        รวมหลายแหล่งพร้อมกัน + ตัดฟ้าผ่าซ้ำข้ามแหล่ง
    replay.py        เล่นข้อมูลจริงที่ capture ไว้ (ฟ้าผ่า + เรดาร์)
    rainviewer.py    ดึงภาพเรดาร์ + ส่งวิเคราะห์
  model/
    tiering.py       วงรัศมี/สถานะจากฟ้าผ่า + นาฬิกา all-clear
    radar_cells.py   สี -> dBZ -> hotspot -> cell -> ระยะถึงสนาม
    nowcast.py       ETA การเคลื่อนที่ (ใช้ทั้งฟ้าผ่าและเรดาร์)
    fusion.py        รวมหลักฐานเป็นสถานะเดียว + กฎ NO_DATA
static/              index.html, app.js, style.css
data/                GeoJSON สนาม, ตารางสีเรดาร์, SQLite, captures/
docs/system_design.md
tests/               test_model, test_blitzortung, test_pipeline, test_availability, test_radar,
                     test_replay_view
                     storm_fixture.py (ข้อมูลสังเคราะห์สำหรับ unit test เท่านั้น)
```

## ทดสอบ

```bash
python -m tests.test_model          # 21 ข้อ  tiering + nowcast
python -m tests.test_blitzortung    # 17 ข้อ  LZW decoder
python -m tests.test_pipeline       # 15 ข้อ  ingest + capture + replay
python -m tests.test_availability   # 41 ข้อ  quota หมด + NO_DATA + fusion + หลายแหล่ง/ตัดซ้ำ
python -m tests.test_radar          # 31 ข้อ  dBZ + cell + ระยะ + replay เรดาร์
python -m tests.test_replay_view    # 18 ข้อ  replay บนหน้าเว็บ ณ เวลาเสมือน
```

ทั้งหมดรันแบบ offline ไม่ต่อเครือข่าย และไม่แตะฐานข้อมูลของโปรเจกต์

## ยังไม่ได้ทำ

- ข้อมูลฟ้าผ่าที่ครบกว่า Blitzortung: รอ quota ของ Xweather รอบเดือน ต.ค. (ระบบจะใช้เสริมเองอัตโนมัติ)
- ชั้นเรดาร์ของ TMD — ไม่มี API
- การแจ้งเตือน push ถึง safety officer
